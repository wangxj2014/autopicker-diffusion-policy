# Autopicker 示范数据与控制接口草案 v0.1

配套[研究方案](2026-11-22-diffusion-policy.md)。这是待实现的数据契约；下列字段、采集目录和策略接口尚未存在，现有接口在文中单独指出。第一版范围为 R_down 单臂、固定机身、一个指定目标、无人工抓偏。

## 1. 身份、单位与坐标

关节数组统一使用以下语义顺序，实际 articulation 索引在每次初始化时按完整名称查找：

| 序号 | R_down 关节名称 | 类型/单位 | 当前范围 |
| --- | --- | --- | --- |
| 0 | `R_down_roll_joint` | 旋转，rad | [-1.2217, 0.261799] |
| 1 | `R_down_hor_joint` | 平移，m | [0, 1.2] |
| 2 | `R_down_ver_joint` | 平移，m | [-0.54, 0] |
| 3 | `R_down_rot_joint` | 旋转，rad | [-1.91, 1.57] |

范围来自当前控制器，录制时还要读取并核对 USD 的有效限位。扩展四臂时，关节组顺序为 `L_down, L_up, R_down, R_up`，相机显示顺序则为 `L_up, R_up, L_down, R_down`；数据按 `arm_name` 和相机路径关联，不按显示位置推断。

基座坐标系定义为 episode 开始时 `/World/Autopicker` 的局部坐标系，固定机身期间保持不变。验证该 prim 存在并记录其世界变换；不把整个 `/World` 的平移或旋转误当成目标变化。目标、接果位置和策略点云统一转换到这个基座系。

现有 `get_depth_frame(arm)` 返回 `rgb`、`depth_m`、`intrinsics`、`world_from_camera`、`reference_time`、`capture_id`、`received_monotonic_s`、`camera_path`。初始化、停止或重建后可能无数据，采集器必须等待新的有效批次。

现有 `world_from_camera` 使用 USD **行向量**约定；相机局部方向为 +X 向右、+Y 向上、-Z 向前。深度是米制光轴深度，不是相机到点的欧氏距离。像素坐标 `u` 向右、`v` 向下：

```text
camera_point = [(u-cx)*depth/fx, -(v-cy)*depth/fy, -depth]
world_point  = camera_point @ world_from_camera[:3, :3] + world_from_camera[3, :3]
base_point   = world_point  @ base_from_world[:3, :3]   + base_from_world[3, :3]
```

其中 `base_from_world = inverse(world_from_base)`，同样采用行向量。保存变换约定和场景米制比例，不能直接把矩阵交给采用列向量的外部库。采用列向量的适配器必须显式转置，并用已知世界点的投影/反投影验证。

## 2. 先记录原始流，再生成训练样本

为每次采集创建一个独立 episode。原始记录包含三个流，保留接收到的数据和时刻，方便重新对齐而不必重新跑仿真：

| 流 | 必须记录的内容 |
| --- | --- |
| 物理状态 | `physics_step`、`sim_time_s`、当前四关节 `q`/`qdot`、实际末端位姿、目标位置、接果位置、`attached` 状态；明示读数在该物理步的哪个阶段 |
| 实际下发命令 | 命令生效步与 `sim_time_s`、写入前后的关节目标、速度前馈、控制模式、限位/限速结果；不能只记录规划器理想路径 |
| 渲染批次 | 每路 RGB/深度/内外参、原始有理数 `reference_time`、`capture_id`、接收墙钟时刻；额外记录经验证的曝光仿真时刻与对齐误差 |

同时记录事件流：目标分配、capture、release/collect、接触、意外落果、超时、停止和异常，均带目标身份和仿真时刻。已有 `records` 只能提供其中部分事件，不能代替这三个流。

每个 episode 保存元数据：数据格式版本、仓库 SHA 与工作区是否干净、USD 文件 SHA256、Isaac 版本、完整控制配置、初始所有关节、初始苹果/树状态、目标 prim 路径、当前臂与相机顺序、内外参约定、采样 dt、控制器/插值器版本、随机种子和数据划分。

### 2.1 时间对齐规则

1. 以仿真时间定义控制周期。墙钟仅用于耗时测量，禁止用 `received_monotonic_s` 替代曝光时间。
2. 先验证渲染 `reference_time` 与当前场景仿真时钟的关系，保存原始分子和分母；不能直接假设它等于当前物理步时间。用已知运动轨迹和渲染相机姿态交叉检查。
3. 首版采用锁步采集：仿真到采样边界后保持物理状态，等待确认属于该边界的新渲染批次，再读取观察并推进下一段动作。等待渲染时若框架仍推进物理，必须改用带时刻的状态缓冲对齐，不能假装锁步成功。
4. 状态缓冲只在已有两端样本之间插值；不对缺失未来状态外推。目标吸附、落果、放果、reset 等离散事件两侧不得跨事件插值。无法对齐的帧标记无效并重采该段或回合。
5. 第一版验收上限为一个物理步，即 1/480 s。没有已验证的时钟映射，或误差超过上限，不能进入干净训练集。
6. 四路扩展时，相机帧必须具有相同 `capture_id` 和 `reference_time`，且属于同一 reset generation。相同 `reference_time` 的重复提交不能当成新的时间样本。

当前 Viewer 受墙钟刷新节流影响，且未实现状态缓冲。拟新增的采集路径需要独立的仿真采样调度；循环调用 UI 接口十次不等于得到十个有效、等间隔的仿真样本。

## 3. 训练样本格式

建议转换为 Zarr v2 的连续数组加 `meta/episode_ends`，适配固定上游 Dataset/SequenceSampler。原始数据与转换数据分别保存，避免把不规则渲染时序直接解释为等间隔动作。

以下 `N` 是该划分中所有 episode 的动作步总数。每个状态 `obs[k]` 在动作开始前读取；最后一次动作之后的终止状态另存供验收，不伪造一个训练动作。

| 字段 | shape / dtype | 含义 |
| --- | --- | --- |
| `data/q` | N×4 float32 | 真实关节位置，原生单位 |
| `data/qdot` | N×4 float32 | 真实关节速度，rad/s 或 m/s |
| `data/goal_base_m` | N×3 float32 | 指定苹果坐标；带 oracle 标签，非视觉检测结果 |
| `data/receiver_base_m` | N×3 float32 | 当前实际接果中心；它随 hor 运动，不能误存为常量 |
| `data/attached` | N×1 float32 | 当前是否携带指定果实，0/1；属于仿真任务状态 |
| `data/rgb` | N×H×W×3 uint8 | 同步 RGB，无深度伪彩色，无 UI 截图 |
| `data/depth_m` | N×H×W float32 | 光轴深度，米；无效像素存为 0 并配合有效掩码使用 |
| `data/depth_valid` | N×H×W bool | 有限且在所选深度范围内的像素；0 深度不是有效表面 |
| `data/intrinsics` | N×3×3 float64 | 对应所保存分辨率及像素中心约定 |
| `data/world_from_camera` | N×4×4 float64 | 曝光时刻的米制行向量变换 |
| `data/action` | N×4 float32 | 下一动作间隔终点的绝对关节位置命令，定义见下一节 |
| `data/sim_time_s` | N float64 | 观察时刻，相邻有效样本间隔为冻结的 dt |
| `data/render_reference_time` | N×2 int64 | 原始渲染时间分子/分母 |
| `data/capture_id` | N int64 | 渲染批次；只在当前 session/generation 内比较 |
| `data/sync_error_s` | N float64 | 经映射后的曝光时刻与状态时刻之差 |
| `meta/episode_ends` | episode 数 int64 | 每回合累计结束索引，右端不包含 |

首个低维观察拼接 `q(4), qdot(4), goal_base_m(3), receiver_base_m(3), attached(1)`，维数 15。专家阶段标签和苹果 prim 路径只作元数据/诊断，不喂入策略；否则模型可能依赖部署时不存在的专家内部状态。

低维实验可省去训练数组中的图像，但原始同步审计小批量必须保留图像和标定。视觉实验的适配器将 RGB 转为 `[B, n_obs_steps, 3, H, W]` 的 float32 `[0,1]`。低维为 `[B, n_obs_steps, 15]`；输出动作块为 `[B, n_action_steps, 4]`。实际序列 Dataset 按上游需要返回完整 `horizon` 的动作，随后由策略截取执行段。

图像缩放必须同时变换内参；例如无裁剪、像素中心对齐的缩放系数为 sx、sy 时，`fx'=sx*fx, cx'=sx*(cx+0.5)-0.5`，y 轴同理。深度和有效掩码用明确的采样规则，不能双线性插值跨越前景/背景产生假表面。原始分辨率和训练分辨率在 manifest 中分别记录。

归一化统计仅来自训练划分；关节按维度处理，不把米和弧度混用。记录 scale/bias、恒定维度处理及模型输出裁剪规则，与 checkpoint 一起保存。验证/测试数据不参与拟合归一化器。

## 4. 动作时间与共同执行器

定义 `action[k]` 为在区间 `[t_k, t_k+dt]` 内要执行到的**命令终点**，即专家命令轨迹在 `t_k+dt` 的值；不是实测 `q[k+1]`，也不是当前命令 `q_cmd[k]`。从原始高频命令重采样得到这些节点，然后用与策略完全相同的执行器回放验收。

执行器从上一个实际下发的命令节点开始插值，按 480 Hz 更新位置目标，并从同一命令轨迹求速度目标；它必须同时满足速度/加速度限制，不能保留原专家旧的速度前馈。首个节点从 reset 后的关节状态初始化。限速导致无法达到请求节点时同时保存 requested/applied 值和原因，用实执行轨迹评估。

原专家使用五次轨迹及接近路径，而低频节点经过新的执行器未必等价。因此先做 10 回合回放验收，检查实际末端误差、姿态、放果与原专家一致；必要时提高采样率/降低采集速度。训练不能建立在“重采样应该等价”的假设上。

以 `n_obs_steps=2, horizon=16, n_action_steps=2` 为例，在当前时刻 k 使用 `obs[k-1:k+1]`；训练动作窗从 `action[k-1]` 开始，推理截取预测索引 `[1:3]`，对应 `action[k]` 和 `action[k+1]`。不能再额外移位一次。序列禁止跨 episode；起止 padding 复用边界值并记录有效长度，避免长 padding 主导训练。episode 结束立即丢弃尚未执行动作。

策略输入必须在推理调用时已可用；未来命令只能作训练标签。仿真附着状态可以作为首版观察，但需记录它是 oracle 状态，真实部署时需要独立检测或估计。

## 5. Reset、失败和策略运行

- Reset 恢复全部关节/命令、目标苹果和已隐藏苹果、树动画、掉落刚体、接果计数、预留目标、观察缓存与动作队列；记录其他三臂的静止姿态。
- Start 等待有效状态与新渲染帧，检查指定目标可达，再开始计时；目标不可达属于 reset/数据准备失败，不伪造成功示范。
- Success 以指定苹果的 collect 事件为准，同时核对实际末端放果位置、接果装置位置和计数。对正确的抓取保留当前 30° 接近方向要求及既有到位条件。
- Failure 分类包括超时、抓偏、非预期落果、无效状态、关节越界、同步失败、推理超时、关闭场景和用户停止；保存原始原因。碰撞指标标明是几何接触近似还是 PhysX 接触。
- 推理请求携带 episode/generation、观察时刻和 dt；回复携带相同标识、动作起始时刻和动作块。验证维度、有限性、顺序、时效和关节范围后才能执行。
- 第一版锁步运行可等候推理，但有有限墙钟超时。后续实时模式若回复迟到，丢弃已过执行时间的动作；剩余动作不足时按执行器约束减速保持并记为失败，不悄悄退回专家后计为策略成功。
- Pause 不推进仿真时间；Stop、stage close 和重新启动必须清空策略队列。原 UI 的生命周期行为保持为回归检查内容。

## 6. 数据验收与复现实验

采集与转换完成后，逐 episode 检查：字段长度一致；数值有限且单位正确；时间严格递增；相邻样本满足 dt；对齐误差达标；reset 不串帧；RGB 与深度/内外参同批；关节不越界；收果事件与目标一致；回放成功。

划分清单使用 `(scene_id, target_prim_path)` 分组，同一目标的重复示范只进入一个划分。新场景泛化采用 scene 级留出。目录结构建议为 `datasets/autopicker/<dataset_version>/`，内含 manifest、划分清单、原始记录和转换 Zarr；训练输出置于 `runs/`。这些目录尚未创建，开始采集前应加入 `.gitignore`，数据和权重存到独立存储，并记录内容校验值。

每次实验保留数据版本、划分、代码版本、模型配置、归一化器、执行器配置、训练种子、策略采样种子、评估目标和 reset 参数、逐回合结果、显存与延迟统计。数据契约、动作 dt 或执行器变更必须升级版本，不复用旧 checkpoint 声称兼容。
